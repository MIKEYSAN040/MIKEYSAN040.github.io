CloudGuard: Diagnosing monitoring failures and automating EC2 recovery

Infrastructure monitoring | Incident detection | Automated recovery

An EC2 monitoring setup that detects high CPU through a custom metric, raises a CloudWatch alarm and triggers a Lambda function to remediate. I built it to understand how a problem travels from detection to recovery.

EC2→CloudWatch Agent→Custom CPU metric→CloudWatch Alarm→Lambda→EC2 reboot
EC2IAMCloudWatchCloudWatch AgentLambdaPython / Boto3Linux logs

What I implemented

  • Dev and prod EC2 instances with IAM roles for monitoring and remediation
  • CloudWatch Agent publishing the custom cpu_usage_user metric
  • Alarm: above 70%, one-minute average
  • Boto3 Lambda function wired to the alarm, tested end to end

Also documented

  • Lambda IAM denial involving ec2:RebootInstances
  • Alarm not triggering as expected
  • Incorrect CloudWatch Agent configuration
Resolved Metrics stopped appearing, alarm in InsufficientData
Problem
I stopped the CloudWatch Agent on purpose. Metrics stopped reaching CloudWatch and the alarm moved to InsufficientData.
Investigation
Checked the agent service state and logs with systemd and journalctl. The agent was no longer running.
Resolution
Restarted the agent.
Validation
Confirmed metric collection resumed and monitoring recovered.
systemctl status amazon-cloudwatch-agent
journalctl -u amazon-cloudwatch-agent --no-pager | tail
Tested High CPU detection and automated recovery
Investigation
Watched the custom CPU metric, set the alarm threshold and checked the alarm-to-Lambda link.
Outcome
Lambda invokes the EC2 remediation action. I tested the alarm and remediation workflow.
Support skills shown: Linux service checks, log analysis, IAM permission failures, alert thresholds, following an incident from detection to recovery.

GlobalM: Linux deployment failure and web availability

Application deployment | Linux administration | Deployment troubleshooting

A website deployed to EC2 through a GitHub-based pipeline. The useful part was finding why a deployment lifecycle step failed.

GitHub→CodePipeline→S3 artifact→CodeDeploy→EC2 + Apache→Live site
EC2CodePipelineCodeDeployS3Amazon Linux 2023ApacheSecurity Groups
Resolved CodeDeploy AfterInstall failed with exit code 127
Problem
The AfterInstall lifecycle stage failed with exit code 127 (command not found).
Investigation
Read the install script. It mixed dnf install httpd with leftover Ubuntu commands (apt-get / apache2), which do not exist on Amazon Linux 2023.
Resolution
Corrected the script to use the package manager for the target OS.
Validation
Checked web server config and files in /var/www/html/, then confirmed the live website loaded.
Also checked
  • CodeDeploy agent status
  • A region mismatch: I was first looking in the wrong AWS region; resources were in ap-southeast-2
sudo systemctl status codedeploy-agent
ls -l /var/www/html/
Support skills shown: reading and fixing scripts, OS compatibility awareness, deployment agents and lifecycle events, web server basics, availability validation.

LMS: Containerised application health and availability

Application support | Containers | Load balancing

A containerised web app on ECS Fargate behind an Application Load Balancer, used to understand how a request reaches a running container and how health is checked.

Docker image→ECR→ECS Fargate→ALB→User
DockerECRECS FargateALBVPCSecurity GroupsCloudWatch Logs

Setup

  • ECR repo lms, image tag v1, region ap-southeast-2
  • Task definition lms-task, Fargate, awsvpc networking, container port 80
  • Load balancer lms-alb with /health endpoint

Validated

  • HTTP request via the ALB returned 200 OK from nginx
  • Healthy tasks showed ALB health checks returning 200
Investigated Task revision lms-task:4 kept stopping
Problem
After updating to lms-task:4, tasks repeatedly stopped with "Essential container in task exited". Revision 3 stayed running.
Investigation
Checked ECS task status and CloudWatch logs. I did not locate the failing task's logs; the logs I found belonged to healthy tasks.
Status
Not claimed as fixed. It is a documented investigation.
Support skills shown: reading task and service status, health checks, basic HTTP troubleshooting, load balancer to backend flow.
